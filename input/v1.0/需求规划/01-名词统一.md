## 〇、项目与本版输入（背景对齐）

| 项 | 内容 |
|----|------|
| 项目名 | 访客系统（学校访客） |
| 业务域 | 校园安全管控 + 来访预约登记 |
| 核心场景 | ① 家长来访**预约**；② 外来人员进校**登记**（两者都要） |
| 核心痛点 | 预约不规范 / 对接低效 / 安全管控弱 / 登记不全、留痕难（四项全中） |
| 参与角色 | 管理员、门卫/保安、被访教职工、访客本人（四类） |
| 业务目标 | **保安全**（来访全流程留痕可查、身份可控、异常可追溯） |
| 系统定位 | 面向中小学校园的访客预约—审核—核验—放行—离校—留痕**闭环管控系统** |

## 一、角色名词（谁在用）

| 名词 | 英文/代号 | 定义 | 主要职责 | 数据范围 |
|------|-----------|------|---------|---------|
| **管理员** | admin | 系统与规则维护者（多为校安全办/信息中心人员） | 维护用户/角色、访客类型、黑名单、时段规则；查看全部访客台账与统计；处理争议与异常 | 全校 |
| **门卫/保安** | guard | 校门值守人员 | 现场核验预约/身份、登记放行、记录进校与离校、异常上报 | 校门当日/现场 |
| **被访教职工** | host | 校内被访问的教职工（教师/行政） | 接收并处理来访预约（同意/拒绝/改期）、确认接待、必要时接待陪同 | **仅本人**相关预约（对象级隔离，§3.22） |
| **访客本人** | visitor | 计划进入校园的非本校在册人员 | 提交预约/现场登记、获取访客凭证、配合核验、离校确认 | 仅本人预约与记录 |

> 补充角色（后续版本可能引入，暂不在 V1.0 主体）：**陪同人/接待部门负责人**、**校领导**（特殊访客审批）。
>
> **访客本人的入口形态**：访客本人使用**移动端访客端（手机 H5）**，**无任何 web / 后台端**（全部在手机端完成，不经过后台统一门户）；V1.0 仅承载「**我要申请**」与「**我的申请（查看）**」两项功能。访客进入访客端的方式有两种：① 到门口由门卫协助/现场登记；② **扫描「申请入口二维码」自助进入**（见 §三）。

## 二、访客与访客分类（分类枚举）

| 名词 | 定义 | 取值/示例 |
|------|------|----------|
| **访客** | 非本校在册人员，因事**临时**进入校园者 | —— |
| **访客类型** | 访客按身份与管控强度的分类（枚举，需求后续穷举） | `家长`（学生家长）、`外来人员`（供应商/维修/检查/快递/其他单位）、`公务来访`（上级/兄弟单位）…… |
| **家长访客** | 学生家长，因家长会/学生事务等来访 | 归属「访客类型=家长」 |
| **外来人员** | 非家长、非公务的校外人员（含施工、维修、送货等） | 归属「访客类型=外来人员」 |
| **公务来访** | 上级主管部门、兄弟学校等公务来访 | 归属「访客类型=公务来访」 |
| **随行人员** | 与主访客同行的其他人员 | 计 1 条预约；**逐人明细登记**（姓名 / 与主访客关系 / 证件号），到访人数以明细条数为准（不再仅记人数） |
| **访客车辆** | 访客驾驶进入校园的机动车 | 记车牌号；是否放行入校按校方规则 |
| **访客端（移动端）** | visitor client / 手机 H5 | 访客本人使用的**手机端界面**（区别于管理员/门卫的**后台桌面端**）；**访客本人无任何 web / 后台端**，全部在手机端完成 | V1.0 仅承载「我要申请」「我的申请（查看）」；不做后台桌面端功能 |

## 三、核心业务动词与流程名词

| 名词 | 英文/代号 | 定义 | 关键口径 |
|------|-----------|------|---------|
| **预约** | appointment / reservation | 访客**来访前**提交的进校申请（含到访时间、事由、被访人） | 须经审核（视规则）后方可核验放行 |
| **现场登记** | on-site registration | 未预约访客到达校门时**现场**补录的信息 | 适用「无预约来访」「临时来访」 |
| **扫码自助申请** | scan-to-apply | 访客**扫描「申请入口二维码」**自助进入移动端访客端并提交预约 | 访客端 V1.0 两大进入方式之一（另一为门口门卫协助 / 现场登记） |
| **申请入口二维码** | apply-entry QR | 后台生成、张贴于校门 / 公示处的二维码，访客扫码即进移动端「我要申请」 | 后台（管理员 / 门卫）可查看 / 下载 / 打印；扫码后打开移动端 H5，无需装 App |
| **审核 / 审批** | review / approval | 被访人或管理员对预约的**同意 / 拒绝 / 改期**处理 | 审核人默认为被访教职工（可配置，见 §3.25） |
| **核验** | verification | 门卫核对**身份信息 + 预约/凭证**是否一致、是否在有效时段 | 核验通过方可放行 |
| **放行** | admit | 允许访客进入校园 | 记录放行时刻与放行人 |
| **进校** | check-in | 访客实际进入校园的动作（记时刻） | 与「放行」可同刻、可分离 |
| **离校** | check-out | 访客离开校园的动作（记时刻） | 未离校形成「在校中」状态，超时未离报警 |
| **访客凭证** | visitor pass / badge | 核验通过后生成的通行凭据 | 形态可为预约编号 + 二维码/短码，闸机或人工核销 |
| **陪同 / 接待陪同** | escort | 校方安排人员全程陪同特定访客（如施工人员） | 触发条件按访客类型/时段规则（可配置） |
| **黑名单** | blacklist | 禁止进校的人员名单 | 命中黑名单→预约/放行被拦 |
| **安全告知 / 承诺** | safety notice / commitment | 访客进校前须阅读并确认的安全须知 | 未确认不放行（按规则） |
| **访客台账** | visitor log | 全部来访记录的汇总（谁、何时、找谁、何时走） | 保安全的**核心留痕载体** |
| **异常** | anomaly | 超时未离校、黑名单命中、信息不符、强行闯入等 | 需上报并留痕 |
| **证件识别** | ID recognition | 门卫核验时读取 / 识别访客身份证件（读卡或拍照 OCR），自动提取姓名、证件号并与预约比对 | 用于核验提速与身份比对；识别失败可回退手工录入（识别结果人工可改，留痕） |
| **现场人像采集** | on-site photo capture | 门卫校门核验时对访客现场拍照留存 | 与本次来访记录绑定；用于事后追溯，非人脸比对（比对能力留后续版本） |
| **邀约 / 邀请码** | invitation / invite code | 被访教职工**主动发起**邀约，生成邀请码 / 链接发给访客，访客凭码快速提交或免填到访 | 与「访客自助申请」互补（一为访客发起、一为被访人发起）；V1.0 生成邀请码，渠道同通知 |
| **常客快登** | frequent-visitor fast check-in | 系统保存曾批准、无黑名单记录的访客信息，再次到访可**一键复用**上次信息快速登记 | 需通过黑名单与证件核验方可放行；常客身份可被校方清除 |
| **访客证 / 临时通行卡** | visitor card / temp pass | 核验通过后发给访客的**物理凭证**（打印贴纸 / 临时卡），或手机端电子凭证的可打印版 | 与「访客凭证」（电子）对应；用于访客在校期间随身识别；离校回收或作废 |
| **车牌识别 / 道闸联动** | ANPR / barrier linkage | 摄像头识别访客车牌，与预约登记车牌比对；可联动道闸自动 / 手动放行 | 校门有车牌识别设备时启用；无设备时门卫手工核对车牌（可配，§3.25） |
| **在校（实时）清单** | on-campus live roster | 当前**仍在校园内**的访客实时名单（谁、何时进、找谁、已在校多久） | 应急疏散 / 突发事件的**安全核心**数据源；与来访台账（历史）区分 |
| **催离** | overtime reminder / eviction nudge | 访客超过预定在校时长（或闭校时刻）仍未离校时，系统提醒访客与门卫 | 超时未离触发（阈值可配，§3.25）；催离动作留痕，并把访客置入待关注清单 |
| **个人信息保护** | personal-info protection | 采集的访客姓名 / 证件号 / 车牌 / 人像等个人信息的合规处理 | 须**授权告知 + 最小必要收集 + 留存期限到期脱敏/清除**（期限可配，§3.25）；访客可索取/更正本人信息（对应 §3.22 对象级隔离） |

## 四、时间、状态与数据口径

### 4.1 时间名词

| 名词 | 定义 | 口径 |
|------|------|------|
| **预约时段 / 到访时段** | 访客约定的预计到访时间窗 | 起止时刻；超窗作废或需改期 |
| **有效时段** | 凭证可核验放行的有效时间范围 | 默认＝预约时段前后缓冲（缓冲值可配置，§3.25） |
| **到访时刻** | 访客实际核验进校的时刻 | 精确到分钟（业务时间，可不补秒，§3.12 排除项） |
| **离校时刻** | 访客实际离校的时刻 | 同上 |
| **在校时长** | 离校时刻 − 到访时刻 | 用于超时告警阈值比对 |

### 4.2 预约/来访状态（状态全集，迁移驱动与时点待需求阶段穷举，§3.23）

| 状态 | 含义 | 说明 |
|------|------|------|
| **待审核** | 预约已提交、尚未处理 | 迁移驱动：被访人/管理员审核 |
| **已通过** | 审核同意，等待到访 | 生成/可用凭证 |
| **已拒绝** | 审核不同意 | 不可放行 |
| **已改期** | 审核建议改到新时段（可再走审核） | 视需求是否单列状态 |
| **已过期** | 超过有效时段未到访 | 超时自动流转（时点待定） |
| **已到访 / 在校中** | 已核验进校、尚未离校 | 离校动作使其流转 |
| **已离校** | 已完成本次来访闭环 | 终态 |
| **已取消** | 访客主动取消预约 | 终态 |

> ⚠️ 上表为**候选全集**，各状态的**迁移驱动（谁/什么事件）× 迁移时点（即时/定时/批量）**将在阶段三需求清单按 §3.23「状态机三件套」逐条闭合，此处仅统一命名。

### 4.3 关键数据口径

| 名词 | 口径 |
|------|------|
| **本校在册人员** | 教师、学生、行政职工等已纳入本校名册者（**非访客**） |
| **访客数统计** | 按「来访记录条数」或「去重人数」口径区分，需求阶段明确 |
| **软状态（在用/停用）** | 访客类型、被访人绑定、门卫账号等**跨周期增减一律用软状态** `status∈{active,inactive}` 代替删除（§3.21）：停用＝退出流程、保留历史、可恢复 |
| **对象级隔离** | 「被访教职工仅本人」「访客仅本人」等边界，**以用户绑定的实体 id 为准**在服务端强制（§3.22），登录 ≠ 有权限 |
| **留痕** | 谁、对什么、何时、结果，敏感操作（审核/放行/失败核验/代登录）均写操作日志（§3.22） |
